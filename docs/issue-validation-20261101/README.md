## 代码确认与处理

- `IKRZGB`：下载地址连续过期时，原代码只刷新两次，随后失败；新增有界恢复，先沿用点歌通知和取址，仍过期时最多重新登录一次。只处理 HTTP 403 且响应明确包含 expired；其他拒绝、429 和服务错误不触发重新登录。
- `IKRUZ4`：原代码已经加密持久化 Cookie，并非每次退出都丢弃登录；无法仅凭反馈判定是服务端会话失效还是本地保存失败。新增自动恢复需要用户在登录页主动勾选加密保存密码；退出登录清除密码与会话。恢复串行化、60 秒冷却，并校验账号与登录代次，防止退出后被旧请求重新登录。
- `IKS2UW`：FFmpeg 6.0 随包头文件 `libavformat/avformat.h` 明确指出 `avformat_seek_file` 忽略 `AVSEEK_FLAG_BACKWARD`。原代码给出的 `max_ts=INT64_MAX` 允许落点晚于目标；修正为目标时间。新定位命令到达后立即停止旧代次解码，丢弃过时的队列重置信息。增加已显示画面的时间戳，回归同时核对视频与播放时钟。
- 不能把上述静态缺陷直接等同于报告者卡顿的全部根因；修复前现有 8 种媒体样本的重唱测试未复现不回零。

## 补充修复：拖动后画面同步、音频未同步

用户补充反馈后，在真正的 MainActivity 双播放器路径复现。此前 88 项检查针对单个 KtvPlaybackEngine，没有覆盖 MainActivity 常驻的第二个原伴唱播放器；先前通过结果不能证明这个组合路径正确。

根因：`prepareExternalVocal` 只在副播放器静音时允许校准位置。当原伴唱切换使副播放器成为当前发声端，拖动进度条、重唱或循环回零都会跳过副播放器的 seek。因此画面/主播放器跳转，正在发声的副播放器继续原来的位置。

处理：用户明确定位时传入 `forceSeek=true`，无论哪个播放器正在发声都同步定位；原伴唱普通切换时仍保留静音侧校准策略。同步覆盖全屏拖动、重唱、单曲循环、指定位置恢复和初始定位。

通过 Debug 专用 DualPlayerSeekTestActivity 驱动真实 MainActivity 的原伴唱按钮及全屏 SeekBar 触摸事件，使用 H.264 + MP1 双音轨样本：

## 限制

本轮没有提供可用于新登录的自有账号密码，因此不宣称真实服务端“连续下载四五首后 403”已复现或实际重新登录已恢复限流。已验证的是错误恢复策略、凭证加密存储，以及本机媒体/下载链路。HTTP 403 本身不能证明一定是限流；只有明确过期响应才进入新恢复分支。
